### v1.6での変更（v1.5からの差分）

v1.5は「メイン画像8枚で26MB」という見積りを前提に、操作予約・写真単位アップロード・保存確定の3段階APIと、それに付随する状態機械・冪等化・起動時リカバリーを設計した。この見積りは変換前の入力容量を引きずった誤りで、実際に送信するのは長辺1920px・品質82%のWebPであり、8枚合計はおおむね3MB程度になる（実測は#102で確定）。

3MB程度であれば1リクエストで送信できるため、v1.6では以下を単純化する。

| 対象 | v1.5 | v1.6 |
| --- | --- | --- |
| アップロード方式 | 操作予約・写真単位アップロード・保存確定の3段階（§10, §11, §16） | 単一リクエスト・単一トランザクション（§10, §16, §19） |
| 状態機械 | 9状態の操作状態（§13, §14） | なし |
| 冪等性 | `operation_id` + `change_set_hash`（§12） | `Idempotency-Key` ヘッダ（§12） |
| 競合後の扱い | アップロード済みファイルを再利用（§12） | 3MB程度を送り直す |
| ファイル最終配置 | SHA-256照合による6分岐の冪等化（§18） | rename一回・失敗時は送り直し |
| 起動時リカバリー | `committing` 状態の回収処理（§23） | なし（`committing` 状態自体が存在しない） |
| GCの保護対象 | 操作状態による保護規則（§25） | なし（保護すべき操作状態がない） |
| バックアップ・復元 | 本書§29・§30で規定 | 実装ではなく運用手順のため本書から除外し、運用ドキュメントへ移す |

`task_photos`（§22）、サーバー側画像検証（§21）、保存パス（§17）、タスク削除（§26）、画像配信（§27）はv1.5から変更していない。

判断の経緯はIssue #99を参照。

## 1. 目的

タスクに写真を登録し、MobileおよびPCから確認できる機能を追加する。

MVPでは、画像をユーザー端末のブラウザで圧縮・WebP変換し、サーバーのDocker Volumeへ保存する。

ロールおよびステータスごとの操作可否は、タスクステータス・権限仕様書に従う。

## 2. 基本仕様

- 1タスクにつき最大8枚
- 0枚でも可
- 複数枚を選択可能
- 表示順は登録順
- 並べ替え不可
- 元画像は保存しない
- 保存画像は静止画WebP
- 写真操作ではステータスを自動変更しない

枚数は次の式で判定する。

```text
保存済みの有効写真数 - 削除予定数 + 追加予定数 <= 8
```

サーバー側では、削除予定を適用した後の有効写真数を使って判定する。

## 3. 表示順

写真テーブルに **sort_order** を保持する。

採番時は、論理削除済みを含む対象タスクの全写真から最大値を取得する。

```text
過去に使用された最大sort_order + 1
```

欠番は詰めず、過去の番号を再利用しない。

複数枚追加時は、操作予約時の画像順序をそのまま連番へ変換する。

クライアントが指定した **sort_order** や写真IDの順序は使用しない。

## 4. ファイル選択

ブラウザ標準のファイル選択UIを使用する。

```html
<input
  type="file"
  accept="image/jpeg,image/png,image/webp,image/heic,image/heif,.jpg,.jpeg,.png,.webp,.heic,.heif"
  multiple
/>
```

- **accept="image/\*"** は使用しない。
- **capture** 属性は指定しない。
- スマートフォンではOSやブラウザが提供するカメラ撮影・写真選択機能を使用する。
- HEIC／HEIFは、ブラウザ標準機能または遅延読み込みするクライアント側デコーダーでWebPへ変換する。
- OSがHEICをJPEGへ変換してブラウザへ渡した場合は、JPEGとして受け付ける。
- 元のHEIC／HEIFをサーバーへ送信または保存しない。

### 対応形式

- JPEG
- PNG
- WebP
- HEIC／HEIF（クライアントでデコードできる場合のみ）

### 対象外

- GIF
- SVG
- AVIF
- その他の形式

非対応形式には次のエラーを表示する。

```text
この画像形式には対応していません。
JPEG、PNG、WebP、HEIC、HEIF形式の画像を選択してください。
```

### HEIC／HEIF

HEIC／HEIFは入力形式としてのみ受け付け、元ファイルをサーバーへ送信・保存しない。

### HEIC／HEIFの判定

拡張子とブラウザが申告するMIMEタイプは、ファイル選択時のヒントとしてのみ使用する。

実際の形式判定ではISO Base Media File Formatの **ftyp** ボックスを解析し、major brandとcompatible brandsを確認する。

- 先頭12バイトだけで形式を断定しない。
- **mif1** や **msf1** は汎用ブランドのため、それだけでHEICと断定しない。
- AVIFのブランドをHEICとして処理しない。
- 判別が曖昧な場合はデコーダーでコンテナとprimary itemの圧縮形式を確認する。
- MIMEタイプが空または **application/octet-stream** でも、実データがHEIC／HEIFなら処理対象にする。

### HEIC／HEIFのデコード

1. ファイルサイズ20MB以下であることを確認する。
2. ブラウザ標準機能でのデコードを試す。
3. 標準機能でデコードできない場合だけ、libheif系WASMデコーダーを遅延読み込みする。
4. WASMデコードはWeb Worker内で実行し、メインスレッドを長時間占有しない。
5. コンテナ内のprimary itemを取得する。
6. デコーダーのセキュリティ制限を有効にしたまま、画素数50MP・長辺12,000pxの上限を確認する。
7. HEIF itemの回転・反転・クロップ指定とEXIF orientationを確認し、表示上の向きを1回だけ適用する。
8. 色空間を8bit sRGBへ正規化し、HDRゲインマップ、深度画像などの補助画像は保存しない。
9. 長辺1920px・品質82%の静止画WebPへ変換する。
10. 変換後の静止画をプレビューする。
11. サーバーには変換後のWebPだけを送信する。

WASMデコーダーはHEIC／HEIFを検出した場合だけ取得する。JPEG・PNG・WebPの処理ではダウンロードしない。

デコーダーのバージョンを固定し、セキュリティ制限を無効化しない。実装時にライセンスと既知の脆弱性を確認する。

デコーダーが向き補正を適用済みかを確認し、HEIF itemの変換指定とEXIF orientationを二重適用しない。

WASMファイルは内容ハッシュ付きの静的アセットとして配信し、長期キャッシュ可能にする。初回読み込みに失敗した場合は、写真選択を失わせず再試行できるようにする。

### HEIC変換中の表示

処理段階に応じて次を表示する。

- **HEIC画像を読み込んでいます**
- **HEIC画像を変換しています**
- **画像を圧縮しています**

進捗率を正確に取得できない処理では、不正確なパーセントを表示せずインジケーターと処理段階を表示する。

デコードまたは変換に失敗した場合は、元ファイルをサーバーへ送信せず次のエラーを表示する。

```text
HEIC画像を変換できませんでした。
別の写真を選択するか、写真を撮り直してください。
```

参考:

- [WebKit Features in Safari 17.0 - HEIC](https://webkit.org/blog/14445/webkit-features-in-safari-17-0/)
- [libheif - Loading the primary image and WebAssembly build](https://github.com/strukturag/libheif)
- [Android supported media formats - HEIF](https://developer.android.com/media/platform/supported-formats)

## 5. 入力画像制限

- ファイルサイズ: 1枚20MB以下
- 総画素数: 50メガピクセル以下
- 長辺: 12,000px以下
- 対応形式: JPEG・PNG・WebP・HEIC・HEIF

50MP画像は、デコード時縮小が利用できる環境でのみ処理する。

### 主処理

**createImageBitmap** のリサイズ機能などを使用し、デコード時に長辺1920px以下へ縮小する。

入力画像と同じ画素数のCanvasは作成しない。

### フォールバック

デコード時縮小を利用できない場合は、次の制限を適用する。

- 12,500,000px以下: Canvas変換を許可
- 12,500,000px超: 変換せずエラー

```text
この端末では画像サイズが大きすぎるため変換できません。
カメラの画質を下げるか、別の画像を選択してください。
```

12,500,000pxは安全側の初期値とし、対象となるiPhone・iPadの実機検証後に調整できる。

## 6. クライアント側画像変換

### メイン画像

- 保存形式: WebP
- 品質: 82%
- 最大寸法: 長辺1920px
- 変換後上限: 1枚3MB
- 縦横比を維持する
- 小さい画像は拡大しない

3MBは圧縮目標ではなく、安全上の拒否上限とする。

品質を段階的に下げる処理は行わない。品質82%で3MBを超えた場合はエラーとする。

### サムネイル

- 保存形式: WebP
- 品質: 75%
- 最大寸法: 長辺480px
- 変換後上限: 1枚300KB
- 縦横比を維持する
- 小さい画像は拡大しない

### 向きとメタデータ

- EXIFの回転情報を反映する。
- 正しい向きへ補正してからWebPへ変換する。
- EXIFと位置情報を削除する。
- 透過部分は白背景へ合成する。
- 縦写真を横向きへ強制回転しない。
- 横長へ強制的に切り抜かない。

### アニメーション画像

アニメーションWebPは、クライアント変換後の先頭フレームを静止画として扱う。

変換後のプレビューに、実際に保存される静止画を表示する。

アニメーション判定のためのRIFFチャンク解析はMVPでは行わない。

### 変換結果の検証

クライアント側で変換後の画像を再デコードし、次を確認する。

- BlobのMIMEタイプが **image/webp**
- 0バイトではない
- 再デコードできる
- 規定寸法以内
- 規定容量以内

WebPエンコード非対応環境ではPNGへフォールバックする可能性があるため、MIMEタイプ検証は省略しない。

黒一色の画像は正常な暗所写真の可能性があるため拒否しない。

## 7. モバイル端末のメモリ対策

画像変換は逐次処理し、同時実行数は1とする。

各画像の処理後に次を行う。

- **ImageBitmap.close()** を呼ぶ。
- Canvasの幅と高さを0へ戻す。
- 不要なObject URLを破棄する。
- 変換済み画像の元のFile参照を解放する。
- プレビューには変換後のBlobを使用する。

8枚を **Promise.all** で同時処理しない。

未処理のファイルと、再試行に必要な処理中ファイルだけ参照を保持する。

## 8. 表示方法

画像表示枠は16:9の横向きとする。

- **object-fit: contain** で表示する。
- 画像全体を表示する。
- 縦写真を切り抜かない。
- 余白は黒または薄いグレーとする。
- サムネイルも画像の向きが分かるように表示する。

## 9. 写真編集と保存前状態

写真の追加・削除は即時確定せず、一時的な変更として扱う。

- 追加写真は保存前にプレビューする。
- 削除操作は削除予定として扱う。
- 「変更保存」で追加・削除・許可されたステータス変更をまとめて確定する。
- 画面を閉じる、別アプリへ移動する、またはページを再読み込みしても、未完了の変更を端末内に一時保存する。
- 有効期限・容量整理・保存確定・ログアウトを除き、利用者が明示的に「変更を破棄」を選択した場合に端末内の下書きを削除する。
- 保存中は二重送信を防止する。

次の状態が1枚でも残る場合、「変更保存」を有効にしない。

- 変換中
- 変換失敗
- 再試行待ち

失敗した写真について、利用者は再試行または取り消しを選択する。

成功した写真だけを暗黙的に保存しない。

### 削除確認

保存済み写真を1枚以上削除する変更セットでは、アップロードセッションを作成する前に確認画面を表示する。

確認画面には次を表示する。

- 追加する写真の枚数
- 削除する保存済み写真の枚数
- 変更先ステータス
- 保存後は画面から削除を取り消せないこと

未保存の追加写真を下書きから取り除くだけの場合は、保存済み写真の削除に含めない。

確認操作:

- **削除して保存**
- **編集に戻る**

Admin向けの写真復元画面はMVP対象外とする。

### IndexedDBへの一時保存

変換済みのメイン画像、サムネイルおよび変更内容をIndexedDBへ保存する。

保存対象:

- ローカル下書きID
- ログインユーザーID
- タスクID
- 取得時の **lock_version**
- 変更先ステータス
- 削除対象写真ID
- 写真の順序
- 変換後のメイン画像Blob
- 変換後のサムネイルBlob
- 各SHA-256と容量
- 各写真の変換状態
- 作成日時・更新日時

v1.5にあった `operation_id` と `expected_lock_version` は、保存が単一リクエストになったことで不要になった（v1.6での変更を参照）。

元のJPEG・PNG・WebP・HEIC／HEIFは、変換完了後にIndexedDBへ保持しない。

各写真の変換完了時、アップロード状態変更時および変更セット更新時に書き込み、ページが非表示になる瞬間の書き込みだけに依存しない。

### 端末内下書きの有効期限

- 最終更新から24時間保持する。
- 保存確定後に削除する。
- 利用者が変更を破棄した場合に削除する。
- 明示的なログアウト時に、そのユーザーの下書きを削除する。
- 別ユーザーでログインした場合、前ユーザーの下書きを表示・再開しない。
- 期限切れ下書きは、アプリケーション起動時および新しい下書きの作成前に削除する。

### 端末内下書きの容量管理

- 同一ブラウザ・同一オリジンに保持する写真下書きは、ログインユーザーをまたいで最大3件とする。
- 新しい下書きの作成前とBlobの保存前に、期限切れ下書きを削除する。
- 期限切れ下書きを削除しても4件以上になる場合は、現在編集中の下書きを除き、最終更新日時が最も古い下書きから削除する。
- 容量整理によって現在の利用者の未完了下書きを削除した場合は、対象タスク名と削除理由を通知する。別ユーザーの下書きを削除した場合は、その内容やタスク名を表示しない。
- **navigator.storage.estimate()** が利用できる場合は、Blobの保存前に使用量と割り当て上限の概算を取得する。
- 保存予定のBlobを加えると容量不足が見込まれる場合は、現在編集中の下書きを除く最古の下書きから削除し、再度見積もる。
- **navigator.storage.estimate()** の値は概算であり、保存成功を保証する判定には使用しない。
- Storage APIを利用できない場合も保存を試み、最終的な容量超過はIndexedDBへの書き込み結果で判定する。

ブラウザによる容量制限やストレージ削除があるため、IndexedDBを唯一の永続データとして扱わない。

IndexedDBへの保存に失敗した場合もメモリ上で作業を続けられるが、次の警告を表示する。

> この端末に写真を一時保存できません。画面を閉じると選択した写真が失われる可能性があります。

### 画面ロック・バックグラウンドからの復帰

サーバー側に操作の概念がなくなったため、**visibilitychange** の監視や自動再開は行わない（v1.6での変更を参照）。

- **hidden** になった場合も、書き込み済みのIndexedDB下書きをそのまま保持する。追加の変換処理は止める。
- **visible** に戻った場合の自動再送は行わない。利用者が下書きを復元し、保存ボタンを押し直す。

ブラウザがバックグラウンドでJavaScriptや通信を継続することには依存しない。Service WorkerのBackground SyncもMVPの必須要件にしない。

### ページ読み込み時の再開

同じログインユーザーの未完了下書きが存在する場合は、次を表示する。

> 途中の写真登録があります。続きから再開しますか？

選択肢:

- **再開する**
- **破棄する**
- **あとで**

**あとで** を選択しても下書きを非表示のまま放置しない。同じタスクの詳細画面を開いた時点で下書きの有効期限を確認し、有効な下書きが存在する場合は、再開・破棄・あとでを選べる再開案内を再表示する。

別タスクを開いている間は再開を強制しない。

**再開する** を選択した場合は、IndexedDBの変換済みBlobをそのまま使って保存前状態を復元する。画像の再選択・再変換は要求しない。復元後は利用者が改めて「変更保存」を押し、単一リクエストで送信し直す（3MB程度のため数秒で完了する）。

### MVPのアップロード開始時点

MVPでは、写真選択直後のバックグラウンドアップロードは行わない。

処理順は次とする。

1. 写真選択
2. 逐次変換
3. IndexedDBへ一時保存
4. 利用者が「変更保存」を押す
5. 単一リクエストで送信し、保存確定する

保存ボタン押下後の所要時間と中断率を実測し、必要な場合は将来、写真選択後の先行アップロードへ変更する。

## 10. 保存リクエスト

v1.5にあった操作予約・写真単位アップロード・保存確定の3段階APIは廃止し、単一リクエストへ統合した（v1.6での変更を参照）。

「変更保存」押下時に、次をまとめた1つのmultipartリクエストを送信する。

- タスクID
- 取得時の **lock_version**
- 削除対象写真ID
- 変更先ステータス
- 追加画像（メイン・サムネイル、登録順）

リクエストはタスクを排他的にロックするものではない。同一タスクに複数ユーザーが同時に送信することを許可し、保存確定時のタスク行ロックと楽観ロックで競合を処理する（§19）。

## 11. （欠番）

v1.5の操作予約は廃止した。詳細はv1.6での変更を参照。

## 12. 冪等性

クライアントは保存リクエストへ `Idempotency-Key` ヘッダ（UUID）を付与する。

サーバーは `idempotency_keys(key, user_id, response_status, response_body, created_at)` へ **key** をUNIQUE制約付きでINSERTする。

- INSERTに成功した場合だけ本処理を開始する。
- UNIQUE制約違反の場合は、保存済みのレスポンスをそのまま返す。
- 保持期間は24時間とする。

**lock_version** 競合や画像検証エラーはリクエストの内容に対する応答であり、`Idempotency-Key` の再利用では解決しない。競合時はクライアントが変更内容を確認し、新しい `Idempotency-Key` で送り直す。

### 競合時の画面

**task_version_conflict** を受け取った場合、単純なエラートーストだけで終了しない。

IndexedDBに保存した変更元スナップショットと最新タスクを比較し、確認画面に次を表示する。

- ステータスの変更前と変更後
- 写真枚数の変更前と変更後
- 写真の追加・削除があったこと
- 物品、数量、担当者、場所、備考など、自分の保存内容に影響する変更
- IndexedDB上の変換済み写真は保持されており、選び直す必要がないこと

表示例:

> 別の利用者がこのタスクを更新しました。
> 最新の内容を確認して、もう一度保存してください。

現在ステータスが未完了で、変更内容が引き続き許可される場合は次を表示する。

- **最新の内容で保存し直す**
- **自分の変更を確認する**
- **変更を破棄する**

最新の写真枚数により8枚を超える場合は、追加写真または既存写真の削除予定を調整するまで保存し直せない。

### 競合後に完了状態だった場合

最新ステータスが完了の場合、写真変更を保存し直すことはできない。

次を表示する。

> このタスクは完了済みのため、写真を追加・削除できません。
> 写真の変更が必要な場合は、Adminにステータスの差し戻しを依頼してください。

- UserおよびLeaderには **閉じる** を表示する。
- Adminには **差し戻しを行う** と **閉じる** を表示する。
- Adminが差し戻す場合も、差し戻し保存と写真変更は別操作にする。
- ローカルの変換済み写真は24時間の有効期限まで保持する（下書きの有効期限。§9参照）。

相手の表示名は、既存の更新監査情報から安全に取得できる場合だけ表示する。取得できない場合は「別の利用者」と表示する。

## 13. （欠番）

v1.5の操作状態の状態機械は廃止した。単一リクエスト・単一トランザクションになったことで、保存は「未送信」→「保存済み」の2状態しか持たない。詳細はv1.6での変更を参照。

## 14. エラー応答

保存リクエストが失敗した場合、DBトランザクションはコミットされない。クライアントは表示されたエラーに応じて修正し、同じ下書きから送り直す。

| 状況 | HTTP | コード | 再試行 |
| --- | ---: | --- | --- |
| タスクが更新済み（`lock_version` 不一致） | 409 | task_version_conflict | 再取得・再確認のうえ送り直す |
| 権限またはステータスが変更された | 403 | permission_or_status_changed | 再取得・再確認 |
| 画像検証失敗 | 422 | image_validation_failed | 該当写真を再変換して送り直す |
| 8枚制限違反 | 422 | photo_limit_exceeded | 追加・削除予定を調整して送り直す |
| 保存先に期待値と異なるファイルが存在する | 409 | storage_key_conflict | 不可・運用通知 |
| 同じ `Idempotency-Key` を処理中 | 409 | idempotency_key_in_progress | 指数バックオフ |

## 15. 再試行地点

保存リクエストが失敗した場合、クライアントは新しい `Idempotency-Key` で同じ下書きを送り直す。v1.5にあった、写真単位の再送信・アップロード済みファイルの再利用という概念はない。1回のリクエストが3MB程度であるため、失敗時は全体を送り直すほうが単純である。

- **画像検証失敗**: 該当写真を再変換してから送り直す。
- **`lock_version` 競合**: 最新タスクを再取得し、変更内容を確認したうえで送り直す。
- **一時的なネットワーク・サーバーエラー**: 同じ内容・新しい `Idempotency-Key` で送り直す。

## 16. 保存リクエストの送受信

1回の「変更保存」につき、追加するメイン画像とサムネイルを含めて1つのmultipartリクエストで送信する（最大8枚）。

- アプリケーション上限: 32MB（メイン3MB・サムネイル300KBの検証上限×8枚の理論上限26.4MBに安全余裕を加えた値。実測の典型値は3MB程度）
- リバースプロキシ上限: 32MB
- タイムアウト: 180秒

受信時に次を検証する（詳細は§19）。

- ログインセッションとタスクの閲覧・操作権限が有効である。
- タスクの現在ステータスが有効である。
- 各画像のMIMEタイプ・容量・寸法が規定内である（§21）。

リバースプロキシでは、保存リクエスト用ルートのリクエストバッファリングを無効化する。アプリケーションはヘッダーと権限を確認してからファイルストリームを一時領域へ保存する。

## 17. 保存パス

一時領域と最終領域は、renameが同一ファイルシステム内で完結するよう同じDocker Volumeへ配置する。

### 一時保存

```text
tmp/{request-id}/{photo-id}/main.webp
tmp/{request-id}/{photo-id}/thumbnail.webp
```

**request-id** は保存リクエストごとにサーバーが生成するUUIDで、DBには保存しない。

### 最終保存

```text
tasks/{task-id}/{photo-id}/main.webp
tasks/{task-id}/{photo-id}/thumbnail.webp
```

写真IDは、DB登録前にサーバーアプリケーション側でUUIDv7として生成する。

クライアントからファイル名、保存キーまたは保存先パスを受け取らない。

**storage_key** はストレージ実装に依存しない論理キーとし、Docker Volumeの絶対パスはDBへ保存しない。

## 18. ファイルの最終配置

各メイン画像とサムネイルについて、次の順序で処理する。

1. 最終ファイルが既に存在する場合、SHA-256が今回のファイルと一致するかを確認する。一致すれば配置済みとして扱い、一致しなければ上書きせず **storage_key_conflict** とする（写真IDはリクエストごとにサーバーが新規採番するため、通常は発生しない。発生した場合は運用エラーとして記録する）。
2. 最終ファイルが存在しない場合、一時ファイルを同一Volume内でrenameする。
3. rename後にSHA-256、容量、形式および寸法を再検証する。

renameに失敗した場合はDBトランザクションを開始せず、リクエスト全体を失敗として返す。クライアントは同じ下書きを新しい `Idempotency-Key` で送り直す。

ファイルrename後・DBコミット前にプロセスが停止した場合、最終ファイルはDBから参照されない孤立ファイルとしてGC対象になる（§25）。

## 19. 保存確定

追加・削除・許可されたステータス変更を、1つのDBトランザクションで確定する。

1. `Idempotency-Key` を確認する（保存済みなら以降を実行せずそのレスポンスを返す。§12）。
2. 権限、現在ステータスおよび **lock_version** を事前確認する。
3. 受信した一時ファイルを検証する（§21）。
4. 一時ファイルを最終位置へ配置する（§18）。DBトランザクション開始前に行う。
5. 最終位置のファイルを再検証する。
6. DBトランザクションを開始する。
7. タスク行をロックする。
8. **lock_version** を再比較する。
9. 権限と現在ステータスを再検証する。
10. 削除対象写真を論理削除する。
11. 削除後の有効写真数を取得する。
12. 「有効写真数 + 追加写真数」が8以下であることを確認する。
13. 論理削除済みを含む最大 **sort_order** から追加分を採番する。
14. 追加写真レコードを登録する。
15. 権限のあるステータス変更を適用する。
16. タスクの **lock_version** を増加させる（DBトリガによる。タスクステータス・権限仕様書を参照）。
17. `task_activities` へ `photo_added` / `photo_deleted` を記録する。
18. `idempotency_keys` へレスポンスを記録する。
19. DBトランザクションをコミットする。

追加・削除・ステータス変更を別トランザクションに分割しない。

一部の最終配置に失敗した場合はDBトランザクションを開始しない。

トランザクションがロールバックされた場合、配置済みの最終ファイルの削除を試みる。削除に失敗した場合はGC対象として放置する（§25）。

## 20. ステータス変更との組み合わせ

写真操作の可否は、タスク行をロックした時点の現在ステータスで判定する。

### 現在ステータスが未完了

- 権限があれば写真を追加・削除できる。
- 権限範囲内のステータス変更と写真変更を同じ変更セットに含められる。
- 写真変更を先に、ステータス変更を後に適用する。
- Adminは写真変更と完了への変更を同時保存できる。
- Leaderは写真変更と未着手・進行中・確認中への変更を同時保存できる。

### 現在ステータスが完了

- Adminを含め、写真を追加・削除できない。
- Adminは差し戻しだけを保存できる。
- 差し戻しと写真変更を同じ変更セットに含められない。
- 差し戻し保存後、新しい **lock_version** で写真を変更する。

## 21. サーバー側画像検証

サーバーはクライアントの申告値を信用せず、受信した実ファイルから値を取得する。

### メイン画像

- MIMEタイプ: image/webp
- ファイルサイズ: 3MB以下
- 幅・高さ: 各1920px以下
- 総画素数: 3,686,400px以下
- 静止画としてデコード可能

### サムネイル

- MIMEタイプ: image/webp
- ファイルサイズ: 300KB以下
- 幅・高さ: 各480px以下
- 静止画としてデコード可能

画像処理ライブラリにはデコード時の画素数制限を設定し、制限を超えた画像を全展開しない。

DBへ保存するMIMEタイプ、容量、幅、高さおよびSHA-256は、サーバーが実ファイルから取得する。

MVPではクライアントが生成したWebPを検証して保存し、サーバー側では再エンコードしない。

INSERT INTO storage_gc_items (...)

## 25. GC

GCは1日1回実行する。

### 削除対象

- mtimeから24時間以上経過した一時ファイル
- mtimeから24時間以上経過した、DBから参照されていない最終ファイル
- **deleted_at** から72時間以上経過した論理削除写真のファイル
- **storage_gc_jobs.delete_after** を過ぎたファイル

v1.5にあった操作状態による保護規則は、保護すべき操作状態自体が存在しなくなったため廃止した。バックアップとの排他制御は運用ドキュメントを参照。

DB上で有効だがファイルが存在しない場合は自動削除せず、運用エラーとして記録する。

## 26. タスク削除

タスクは現行実装どおり、**tasks.deleted** に削除日時を設定して論理削除する。写真機能の追加を理由に、タスクを物理削除へ変更しない。

同じDBトランザクション内で次を行う。

1. 未削除のタスク行をロックする。
2. 削除権限を検証する。
3. 有効な写真の写真IDと保存キーを取得する。
4. 監査ログを保存する。
5. **storage_gc_jobs** を作成する。
6. **storage_gc_items** を、保存キー重複時は **ON CONFLICT DO NOTHING** で登録する。
7. 有効な写真へ、同一の削除日時と実行ユーザーを **deleted_at**、**deleted_by** として設定する。
8. タスクへ同じ削除日時を **deleted** として設定し、**lock_version** を増加させる。
9. コミットする。

写真レコードとタスク行は物理削除せず、監査・GC・復旧判断に必要な情報を保持する。

GCジョブの **delete_after** はタスクの論理削除から72時間後とする。

GCジョブと監査ログは、削除対象の写真やタスクへの外部キーを持たない。

タスク削除対象のファイルは、mtimeが24時間を超えていても **delete_after** より前に削除しない。

72時間の根拠（バックアップ許容上限との関係）は運用ドキュメントを参照。Volume使用量、誤削除の発見時間および復旧実績に応じて見直す。

GCは1日1回のため、排他処理や失敗がない通常時の実際の物理削除は、論理削除からおおむね72〜96時間後となる。

## 27. 画像配信

Docker Volumeを公開ディレクトリとして直接配信せず、認証付きAPIを経由する。

画像取得時に毎回次を確認する。

- ログイン状態
- 対象タスクの閲覧権限
- 対象タスクが論理削除されていないこと
- 写真が論理削除されていないこと
- 写真とタスクの関連

### 200レスポンス

```http
Cache-Control: private, no-cache
Content-Type: image/webp
Content-Length: {actual-byte-size}
ETag: "{sha256}"
X-Content-Type-Options: nosniff
```

メイン画像は **main_sha256**、サムネイルは **thumbnail_sha256** を強いETagとして使用する。

### 304レスポンス

```http
Cache-Control: private, no-cache
ETag: "{sha256}"
```

304には **Content-Type** と **Content-Length** を付与しない。

ETagを比較する前に、必ず認証・認可と論理削除状態を検証する。

論理削除によってSHA-256は変化しないが、毎回認可と論理削除状態を確認するため、削除済み画像へ304を返さない。

現行Figmaでは一覧へ多数のサムネイルを並べないため、MVPではメイン画像とサムネイルの両方に **private, no-cache** を使用する。

将来、多数のサムネイルを一覧表示する場合は、サムネイルだけ短時間キャッシュすることを再検討する。

## 28. インフラ設定

- 保存リクエスト1回あたりのアプリケーション上限: 32MB
- リバースプロキシのリクエスト上限: 32MB
- 保存リクエストのタイムアウト: 180秒

リバースプロキシでは、保存リクエスト用ルートのリクエストバッファリングを無効化する。

- HEIC／HEIFデコーダーの読み込みに失敗した
- 入力ファイルが20MBを超えている
- 入力画素数または長辺が上限を超えている
- ブラウザで安全に変換できない
- WebP変換に失敗した
- メイン画像を3MB以下にできない
- サムネイルを300KB以下にできない
- 最大8枚を超えている
- アップロードに失敗した
- タスクがほかのユーザーによって更新された
- 権限またはステータスが変更された
- 保存先に期待値と異なるファイルが存在する

変換フェーズでは写真ごとに再試行できる。

保存確定フェーズでは変更セット全体を再試行する。

## 36. 受け入れ条件

- JPEG・PNG・WebP・HEIC・HEIFを選択できる。
- 拡張子やMIMEタイプが不正確でも、実データからHEIC／HEIFを判定できる。
- ブラウザ標準機能でHEIC／HEIFをデコードできない場合、WASMデコーダーを遅延読み込みできる。
- HEIC／HEIFコンテナのprimary itemを端末側で静止画WebPへ変換できる。
- HEIC／HEIF変換中に処理段階を表示できる。
- HEIC／HEIFの元画像をサーバーへ送信・保存しない。
- 端末側で静止画WebPへ変換できる。
- 長辺1920px・品質82%を基本として圧縮できる。
- EXIFの向きを反映し、位置情報を削除できる。
- 最大8枚まで登録できる。
- 写真を登録順に表示できる。
- 縦写真を切り抜かずに表示できる。
- MobileとPCの両方で写真を確認できる。
- 完了中は全ロールで写真を変更できない。
- 追加・削除・ステータス変更を1つのDBトランザクションで確定できる。
- ファイルを最終位置へ配置してからDBをコミットできる。
- 同じ `Idempotency-Key` での再送に対して保存済みレスポンスを返し、写真を重複登録しない。
- 変換済み画像と変更内容をIndexedDBへ保持できる。
- 新しい下書きの作成前に期限切れ下書きを削除できる。
- 端末内の写真下書きを最大3件に制限し、容量不足が見込まれる場合に古い下書きから整理できる。
- 画面ロック、別アプリへの移動、再読み込み後に下書きから写真登録を再開できる。
- **あとで** を選択した下書きを、対象タスクの詳細画面から再開できる。
- IndexedDBへ保存できない場合にデータ消失の可能性を案内できる。
- 競合時に変更内容を表示し、選び直さずもう一度保存できることを案内できる。
- 完了との競合時にAdminへの差し戻し依頼を案内できる。
- 保存済み写真を削除する前に削除枚数を確認できる。
- 一覧から確認中・写真ありのタスクを優先して判別できる。
- GC明細が重複してもタスク削除を失敗させない。
- タスク削除時にタスクと有効な写真を同じDBトランザクションで論理削除できる。
- タスク削除対象の写真ファイルを、論理削除から72時間より前に物理削除しない。
- 論理削除済みタスクの写真を画像配信APIから取得できない。
- 未認証ユーザーが画像へ直接アクセスできない。

DBバックアップ・復元・サムネイル再生成に関する受け入れ条件は[運用ドキュメント](operations/task-photo-backup-restore.md)を参照。
