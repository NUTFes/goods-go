## 1. 目的

タスクに写真を登録し、MobileおよびPCから確認できる機能を追加する。

MVPでは、画像をユーザー端末のブラウザで圧縮・WebP変換し、サーバーのDocker Volumeへ保存する。

ロールおよびステータスごとの操作可否は、タスクステータス・権限仕様書に従う。

## 2. 基本仕様

- 1タスクにつき最大8枚
- 0枚でも可
- 複数枚を選択可能
- 表示順は登録順
- 並べ替え不可
- 元画像は保存しない
- 保存画像は静止画WebP
- 写真操作ではステータスを自動変更しない

枚数は次の式で判定する。

```text
保存済みの有効写真数 - 削除予定数 + 追加予定数 <= 8
```

サーバー側では、削除予定を適用した後の有効写真数を使って判定する。

## 3. 表示順

写真テーブルに **sort_order** を保持する。

採番時は、論理削除済みを含む対象タスクの全写真から最大値を取得する。

```text
過去に使用された最大sort_order + 1
```

欠番は詰めず、過去の番号を再利用しない。

複数枚追加時は、操作予約時の画像順序をそのまま連番へ変換する。

クライアントが指定した **sort_order** や写真IDの順序は使用しない。

## 4. ファイル選択

ブラウザ標準のファイル選択UIを使用する。

```html
<input
  type="file"
  accept="image/jpeg,image/png,image/webp,image/heic,image/heif,.jpg,.jpeg,.png,.webp,.heic,.heif"
  multiple
/>
```

- **accept="image/\*"** は使用しない。
- **capture** 属性は指定しない。
- スマートフォンではOSやブラウザが提供するカメラ撮影・写真選択機能を使用する。
- HEIC／HEIFは、ブラウザ標準機能または遅延読み込みするクライアント側デコーダーでWebPへ変換する。
- OSがHEICをJPEGへ変換してブラウザへ渡した場合は、JPEGとして受け付ける。
- 元のHEIC／HEIFをサーバーへ送信または保存しない。

### 対応形式

- JPEG
- PNG
- WebP
- HEIC／HEIF（クライアントでデコードできる場合のみ）

### 対象外

- GIF
- SVG
- AVIF
- その他の形式

非対応形式には次のエラーを表示する。

```text
この画像形式には対応していません。
JPEG、PNG、WebP、HEIC、HEIF形式の画像を選択してください。
```

### HEIC／HEIF

HEIC／HEIFは入力形式としてのみ受け付け、元ファイルをサーバーへ送信・保存しない。

### HEIC／HEIFの判定

拡張子とブラウザが申告するMIMEタイプは、ファイル選択時のヒントとしてのみ使用する。

実際の形式判定ではISO Base Media File Formatの **ftyp** ボックスを解析し、major brandとcompatible brandsを確認する。

- 先頭12バイトだけで形式を断定しない。
- **mif1** や **msf1** は汎用ブランドのため、それだけでHEICと断定しない。
- AVIFのブランドをHEICとして処理しない。
- 判別が曖昧な場合はデコーダーでコンテナとprimary itemの圧縮形式を確認する。
- MIMEタイプが空または **application/octet-stream** でも、実データがHEIC／HEIFなら処理対象にする。

### HEIC／HEIFのデコード

1. ファイルサイズ20MB以下であることを確認する。
2. ブラウザ標準機能でのデコードを試す。
3. 標準機能でデコードできない場合だけ、libheif系WASMデコーダーを遅延読み込みする。
4. WASMデコードはWeb Worker内で実行し、メインスレッドを長時間占有しない。
5. コンテナ内のprimary itemを取得する。
6. デコーダーのセキュリティ制限を有効にしたまま、画素数50MP・長辺12,000pxの上限を確認する。
7. HEIF itemの回転・反転・クロップ指定とEXIF orientationを確認し、表示上の向きを1回だけ適用する。
8. 色空間を8bit sRGBへ正規化し、HDRゲインマップ、深度画像などの補助画像は保存しない。
9. 長辺1920px・品質82%の静止画WebPへ変換する。
10. 変換後の静止画をプレビューする。
11. サーバーには変換後のWebPだけを送信する。

WASMデコーダーはHEIC／HEIFを検出した場合だけ取得する。JPEG・PNG・WebPの処理ではダウンロードしない。

デコーダーのバージョンを固定し、セキュリティ制限を無効化しない。実装時にライセンスと既知の脆弱性を確認する。

デコーダーが向き補正を適用済みかを確認し、HEIF itemの変換指定とEXIF orientationを二重適用しない。

WASMファイルは内容ハッシュ付きの静的アセットとして配信し、長期キャッシュ可能にする。初回読み込みに失敗した場合は、写真選択を失わせず再試行できるようにする。

### HEIC変換中の表示

処理段階に応じて次を表示する。

- **HEIC画像を読み込んでいます**
- **HEIC画像を変換しています**
- **画像を圧縮しています**

進捗率を正確に取得できない処理では、不正確なパーセントを表示せずインジケーターと処理段階を表示する。

デコードまたは変換に失敗した場合は、元ファイルをサーバーへ送信せず次のエラーを表示する。

```text
HEIC画像を変換できませんでした。
別の写真を選択するか、写真を撮り直してください。
```

参考:

- [WebKit Features in Safari 17.0 - HEIC](https://webkit.org/blog/14445/webkit-features-in-safari-17-0/)
- [libheif - Loading the primary image and WebAssembly build](https://github.com/strukturag/libheif)
- [Android supported media formats - HEIF](https://developer.android.com/media/platform/supported-formats)

## 5. 入力画像制限

- ファイルサイズ: 1枚20MB以下
- 総画素数: 50メガピクセル以下
- 長辺: 12,000px以下
- 対応形式: JPEG・PNG・WebP・HEIC・HEIF

50MP画像は、デコード時縮小が利用できる環境でのみ処理する。

### 主処理

**createImageBitmap** のリサイズ機能などを使用し、デコード時に長辺1920px以下へ縮小する。

入力画像と同じ画素数のCanvasは作成しない。

### フォールバック

デコード時縮小を利用できない場合は、次の制限を適用する。

- 12,500,000px以下: Canvas変換を許可
- 12,500,000px超: 変換せずエラー

```text
この端末では画像サイズが大きすぎるため変換できません。
カメラの画質を下げるか、別の画像を選択してください。
```

12,500,000pxは安全側の初期値とし、対象となるiPhone・iPadの実機検証後に調整できる。

## 6. クライアント側画像変換

### メイン画像

- 保存形式: WebP
- 品質: 82%
- 最大寸法: 長辺1920px
- 変換後上限: 1枚3MB
- 縦横比を維持する
- 小さい画像は拡大しない

3MBは圧縮目標ではなく、安全上の拒否上限とする。

品質を段階的に下げる処理は行わない。品質82%で3MBを超えた場合はエラーとする。

### サムネイル

- 保存形式: WebP
- 品質: 75%
- 最大寸法: 長辺480px
- 変換後上限: 1枚300KB
- 縦横比を維持する
- 小さい画像は拡大しない

### 向きとメタデータ

- EXIFの回転情報を反映する。
- 正しい向きへ補正してからWebPへ変換する。
- EXIFと位置情報を削除する。
- 透過部分は白背景へ合成する。
- 縦写真を横向きへ強制回転しない。
- 横長へ強制的に切り抜かない。

### アニメーション画像

アニメーションWebPは、クライアント変換後の先頭フレームを静止画として扱う。

変換後のプレビューに、実際に保存される静止画を表示する。

アニメーション判定のためのRIFFチャンク解析はMVPでは行わない。

### 変換結果の検証

クライアント側で変換後の画像を再デコードし、次を確認する。

- BlobのMIMEタイプが **image/webp**
- 0バイトではない
- 再デコードできる
- 規定寸法以内
- 規定容量以内

WebPエンコード非対応環境ではPNGへフォールバックする可能性があるため、MIMEタイプ検証は省略しない。

黒一色の画像は正常な暗所写真の可能性があるため拒否しない。

## 7. モバイル端末のメモリ対策

画像変換は逐次処理し、同時実行数は1とする。

各画像の処理後に次を行う。

- **ImageBitmap.close()** を呼ぶ。
- Canvasの幅と高さを0へ戻す。
- 不要なObject URLを破棄する。
- 変換済み画像の元のFile参照を解放する。
- プレビューには変換後のBlobを使用する。

8枚を **Promise.all** で同時処理しない。

未処理のファイルと、再試行に必要な処理中ファイルだけ参照を保持する。

## 8. 表示方法

画像表示枠は16:9の横向きとする。

- **object-fit: contain** で表示する。
- 画像全体を表示する。
- 縦写真を切り抜かない。
- 余白は黒または薄いグレーとする。
- サムネイルも画像の向きが分かるように表示する。

## 9. 写真編集と保存前状態

写真の追加・削除は即時確定せず、一時的な変更として扱う。

- 追加写真は保存前にプレビューする。
- 削除操作は削除予定として扱う。
- 「変更保存」で追加・削除・許可されたステータス変更をまとめて確定する。
- 画面を閉じる、別アプリへ移動する、またはページを再読み込みしても、未完了の変更を端末内に一時保存する。
- 有効期限・容量整理・保存確定・ログアウトを除き、利用者が明示的に「変更を破棄」を選択した場合に端末内の下書きを削除する。
- 保存中は二重送信を防止する。

次の状態が1枚でも残る場合、「変更保存」を有効にしない。

- 変換中
- 変換失敗
- 再試行待ち

失敗した写真について、利用者は再試行または取り消しを選択する。

成功した写真だけを暗黙的に保存しない。

### 削除確認

保存済み写真を1枚以上削除する変更セットでは、アップロードセッションを作成する前に確認画面を表示する。

確認画面には次を表示する。

- 追加する写真の枚数
- 削除する保存済み写真の枚数
- 変更先ステータス
- 保存後は画面から削除を取り消せないこと

未保存の追加写真を下書きから取り除くだけの場合は、保存済み写真の削除に含めない。

確認操作:

- **削除して保存**
- **編集に戻る**

Admin向けの写真復元画面はMVP対象外とする。

### IndexedDBへの一時保存

変換済みのメイン画像、サムネイルおよび変更内容をIndexedDBへ保存する。

保存対象:

- ローカル下書きID
- ログインユーザーID
- タスクID
- 操作予約後のoperation ID
- expected lock version
- 変更元のタスクスナップショット
- 変更先ステータス
- 削除対象写真ID
- 写真の順序
- 変換後のメイン画像Blob
- 変換後のサムネイルBlob
- 各SHA-256と容量
- 各写真の変換・アップロード状態
- 作成日時・更新日時

元のJPEG・PNG・WebP・HEIC／HEIFは、変換完了後にIndexedDBへ保持しない。

各写真の変換完了時、アップロード状態変更時および変更セット更新時に書き込み、ページが非表示になる瞬間の書き込みだけに依存しない。

### 端末内下書きの有効期限

- 最終更新から24時間保持する。
- 保存確定後に削除する。
- 利用者が変更を破棄した場合に削除する。
- 明示的なログアウト時に、そのユーザーの下書きを削除する。
- 別ユーザーでログインした場合、前ユーザーの下書きを表示・再開しない。
- 期限切れ下書きは、アプリケーション起動時および新しい下書きの作成前に削除する。

### 端末内下書きの容量管理

- 同一ブラウザ・同一オリジンに保持する写真下書きは、ログインユーザーをまたいで最大3件とする。
- 新しい下書きの作成前とBlobの保存前に、期限切れ下書きを削除する。
- 期限切れ下書きを削除しても4件以上になる場合は、現在編集中の下書きを除き、最終更新日時が最も古い下書きから削除する。
- 容量整理によって現在の利用者の未完了下書きを削除した場合は、対象タスク名と削除理由を通知する。別ユーザーの下書きを削除した場合は、その内容やタスク名を表示しない。
- **navigator.storage.estimate()** が利用できる場合は、Blobの保存前に使用量と割り当て上限の概算を取得する。
- 保存予定のBlobを加えると容量不足が見込まれる場合は、現在編集中の下書きを除く最古の下書きから削除し、再度見積もる。
- **navigator.storage.estimate()** の値は概算であり、保存成功を保証する判定には使用しない。
- Storage APIを利用できない場合も保存を試み、最終的な容量超過はIndexedDBへの書き込み結果で判定する。

容量整理で削除する下書きに有効なoperation IDがある場合は、サーバーへ操作中止を通知する。通知に失敗した場合もローカル削除を妨げず、サーバー側の無活動期限切れとGCで回収する。

ブラウザによる容量制限やストレージ削除があるため、IndexedDBを唯一の永続データとして扱わない。

IndexedDBへの保存に失敗した場合もメモリ上で作業を続けられるが、次の警告を表示する。

> この端末に写真を一時保存できません。画面を閉じると選択した写真が失われる可能性があります。

### 画面ロック・バックグラウンドからの復帰

**visibilitychange** を監視する。

- **hidden** になった場合、現在状態を可能な範囲で保存し、追加の変換・アップロード開始を止める。
- **visible** に戻った場合、サーバー上の操作状態とIndexedDBの状態を照合する。
- 保存操作開始後で未送信写真がある場合、認証・権限・lock versionを再確認して自動再開する。
- オフラインの場合は再開待ちとし、オンライン復帰後に再開する。

ブラウザがバックグラウンドでJavaScriptや通信を継続することには依存しない。Service WorkerのBackground SyncもMVPの必須要件にしない。

### ページ読み込み時の再開

同じログインユーザーの未完了下書きが存在する場合は、次を表示する。

> 途中の写真登録があります。続きから再開しますか？

選択肢:

- **再開する**
- **破棄する**
- **あとで**

**あとで** を選択しても下書きを非表示のまま放置しない。同じタスクの詳細画面を開いた時点で下書きの有効期限を確認し、有効な下書きが存在する場合は、再開・破棄・あとでを選べる再開案内を再表示する。

別タスクを開いている間は再開を強制しない。

サーバー側のoperation IDが有効な場合は、アップロード済みファイルを再利用する。

サーバー側の操作が期限切れの場合は、IndexedDBの変換済みBlobを再利用して新しいoperation IDを予約する。画像の再選択・再変換は要求しない。

### MVPのアップロード開始時点

MVPでは、写真選択直後のバックグラウンドアップロードは行わない。

処理順は次とする。

1. 写真選択
2. 逐次変換
3. IndexedDBへ一時保存
4. 利用者が「変更保存」を押す
5. 操作予約
6. 逐次アップロード
7. 保存確定

保存ボタン押下後の所要時間と中断率を実測し、必要な場合は将来、写真選択後の先行アップロードへ変更する。

## 10. アップロードセッション

画像本体を送信する前に、変更操作をアップロードセッションとして登録する。

セッションはタスクを排他的にロックするものではない。

同一タスクに複数ユーザーのセッションが存在することを許可し、保存確定時のタスク行ロックと楽観ロックで競合を処理する。

後から保存確定する操作が競合する可能性はあるが、30分間の擬似ロックでほかの利用者を阻害しないことを優先する。

## 11. 操作予約

クライアントは、画像本体を送る前に小さなJSONリクエストを送信する。

含める情報:

- **operation_id**
- タスクID
- **expected_lock_version**
- 削除対象写真ID
- 変更先ステータス
- 追加画像の順序
- メイン画像のSHA-256と容量
- サムネイルのSHA-256と容量

サーバーは次を事前確認する。

- 認証
- タスクの閲覧・操作権限
- 現在ステータス
- 現在の **lock_version**
- 追加予定枚数
- リクエスト形式

事前確認は早期拒否のための最適化であり、保存確定時の検証を省略しない。

## 12. 冪等性

**operation_id** はUUIDとし、UNIQUE制約を設定する。

最初にINSERTできたリクエストだけが処理を開始できる。

### change_set_hash

次を正規化したJSONからSHA-256を算出する。

- タスクID
- 削除対象写真ID
- 変更先ステータス
- 追加画像の順序
- 各メイン画像のSHA-256と容量
- 各サムネイルのSHA-256と容量

**expected_lock_version** は変更セットの同一性ではなく事前条件であるため、ハッシュに含めない。

クライアントで画像を再変換した場合、または変更セットの内容を変えた場合は、新しい **operation_id** を発行する。

アップロード時にサーバー側でもSHA-256を計算し、予約内容と一致することを確認する。

### 競合後の再利用

**lock_version** 競合時はアップロード済みファイルを保持する。

1. 最新タスクを再取得する。
2. 利用者が変更内容を再確認する。
3. 同じ変更内容を維持する場合だけ、**expected_lock_version** を更新する。
4. 同じ **operation_id** で保存確定を再試行する。

新しいバージョンへ自動的に読み替えて保存してはならない。

変更内容を変える場合は、既存操作を中止し、新しい **operation_id** を発行する。

### 競合時の画面

**task_version_conflict** を受け取った場合、単純なエラートーストだけで終了しない。

IndexedDBに保存した変更元スナップショットと最新タスクを比較し、確認画面に次を表示する。

- ステータスの変更前と変更後
- 写真枚数の変更前と変更後
- 写真の追加・削除があったこと
- 物品、数量、担当者、場所、備考など、自分の保存内容に影響する変更
- 自分が変換・アップロードした写真は保持されていること

表示例:

> 別の利用者がこのタスクを更新しました。
> あなたが追加した写真は保持されています。最新の内容を確認して保存し直してください。

現在ステータスが未完了で、変更内容が引き続き許可される場合は次を表示する。

- **最新の内容で保存し直す**
- **自分の変更を確認する**
- **変更を破棄する**

最新の写真枚数により8枚を超える場合は、追加写真または既存写真の削除予定を調整するまで保存し直せない。

### 競合後に完了状態だった場合

最新ステータスが完了の場合、写真変更を保存し直すことはできない。

次を表示する。

> このタスクは完了済みのため、写真を追加・削除できません。
> 写真の変更が必要な場合は、Adminにステータスの差し戻しを依頼してください。

- UserおよびLeaderには **閉じる** を表示する。
- Adminには **差し戻しを行う** と **閉じる** を表示する。
- Adminが差し戻す場合も、差し戻し保存と写真変更は別操作にする。
- ローカルの変換済み写真は24時間の有効期限まで保持する。
- サーバー上のアップロード済みファイルは、操作の有効期限まで保持する。

相手の表示名は、既存の更新監査情報から安全に取得できる場合だけ表示する。取得できない場合は「別の利用者」と表示する。

## 13. 操作状態

| 状態             | 意味                                 |
| ---------------- | ------------------------------------ |
| reserved         | 操作予約済み                         |
| uploading        | ファイルアップロード中               |
| ready            | 全追加ファイルのアップロード完了     |
| committing       | 最終配置およびDB確定処理中           |
| conflicted       | lock_version競合、利用者の再確認待ち |
| committed        | 保存確定済み                         |
| failed_retryable | 同じ操作で再試行可能な失敗           |
| failed_terminal  | 同じ操作では再試行できない失敗       |
| aborted          | 取消または期限切れ                   |

### 状態遷移

| 現在状態                               | 条件                           | 次状態           |
| -------------------------------------- | ------------------------------ | ---------------- |
| なし                                   | 操作予約成功                   | reserved         |
| reserved                               | 最初のファイル送信開始         | uploading        |
| uploading                              | 一部ファイルの一時保存失敗     | failed_retryable |
| failed_retryable                       | 該当ファイルを再送信           | uploading        |
| uploading                              | 全ファイルの一時保存完了       | ready            |
| reserved／uploading／ready             | バージョン競合                 | conflicted       |
| conflicted                             | 再取得・再確認完了、未送信あり | uploading        |
| conflicted                             | 再取得・再確認完了、全送信済み | ready            |
| ready                                  | 保存確定開始                   | committing       |
| committing                             | DBコミット成功                 | committed        |
| committing                             | バージョン競合                 | conflicted       |
| committing                             | 一時的な処理失敗               | failed_retryable |
| failed_retryable                       | 保存確定だけ再試行             | committing       |
| 任意の未完了状態                       | 回復不能な検証エラー           | failed_terminal  |
| 任意の未完了状態                       | 利用者が取り消し               | aborted          |
| reserved／uploading／ready／conflicted | 30分間無活動                   | aborted          |
| committing                             | 30分間無活動                   | failed_retryable |

**ready** は、すべての追加写真が **uploaded_temp** または **moved_final** になった時点で設定する。

**committing** は、保存確定の事前確認に成功し、最終配置処理を開始する直前に設定する。

## 14. 失敗時の状態更新

操作予約後に正常完了しなかったすべての場合について、本体処理とは別のDBトランザクションで状態とエラー結果を記録する。

対象:

- 画像検証失敗
- アップロード失敗
- 権限検証失敗
- ステータス検証失敗
- 8枚制限違反
- 楽観ロック競合
- DBトランザクションのロールバック
- その他の例外

成功結果は、写真変更と同じDBトランザクション内で **committed** として記録する。

### エラー応答

| 状況                 | HTTP | コード                   | 再試行             |
| -------------------- | ---: | ------------------------ | ------------------ |
| 同じ操作が処理中     |  409 | operation_in_progress    | 指数バックオフ     |
| 同じIDで内容が異なる |  409 | operation_id_conflict    | 新しいIDが必要     |
| タスクが更新済み     |  409 | task_version_conflict    | 再取得・再確認     |
| 別ユーザーの操作     |  403 | operation_owner_mismatch | 不可               |
| セッション期限切れ   |  410 | operation_expired        | 新しいIDが必要     |
| 写真の再送信が必要   |  409 | upload_required          | 該当写真のみ再送信 |
| 保存先の内容が不一致 |  409 | storage_key_conflict     | 不可・運用通知     |

## 15. 再試行地点

### アップロード失敗

- 該当写真だけ再アップロードする。
- 成功済みのほかの写真は再利用する。
- 同じ **operation_id** を使用する。

### 保存確定の一時的失敗

- 保存確定APIだけを再試行する。
- アップロード済みファイルは再利用する。

### lock_version競合

- 操作を **conflicted** にする。
- タスクを再取得する。
- 利用者が変更内容を再確認する。
- **expected_lock_version** を更新する。
- 保存確定APIだけを再試行する。

### 内容変更

写真、削除対象、順序、変更先ステータスのいずれかを変更した場合は、新しい **operation_id** を発行する。

## 16. ファイルアップロード

1リクエストにつき、1写真分のメイン画像とサムネイルを送信する。

- アプリケーション上限: 4MB
- リバースプロキシ上限: 8MB
- タイムアウト: 180秒
- 同時アップロード数: 1

32MBの一括アップロードは行わない。

アップロード時に次を検証する。

- 操作のユーザーIDとログインユーザーが一致する。
- 操作がアップロード可能な状態である。
- 写真IDが操作明細に含まれる。
- タスクの権限と現在ステータスが有効である。
- 現在の **lock_version** が **expected_lock_version** と一致する。
- SHA-256と容量が予約内容と一致する。
- MIMEタイプと実画像の寸法が規定内である。

競合を検出した場合は残りの画像を送信せず、操作を **conflicted** にする。

アップロード用の独自トークンは設けない。ログインセッションと操作所有者の一致によって認可する。

アップロード用ルートでは、リバースプロキシのリクエストバッファリングを無効化する。アプリケーションはヘッダーと操作情報を確認してからファイルストリームを保存する。

## 17. 保存パス

一時領域と最終領域は、renameが同一ファイルシステム内で完結するよう同じDocker Volumeへ配置する。

### 一時保存

```text
tmp/{operation-id}/{photo-id}/main.webp
tmp/{operation-id}/{photo-id}/thumbnail.webp
```

### 最終保存

```text
tasks/{task-id}/{photo-id}/main.webp
tasks/{task-id}/{photo-id}/thumbnail.webp
```

写真IDは、DB登録前にサーバーアプリケーション側でUUIDv7として生成する。

クライアントからファイル名、保存キーまたは保存先パスを受け取らない。

**storage_key** はストレージ実装に依存しない論理キーとし、Docker Volumeの絶対パスはDBへ保存しない。

## 18. ファイルの最終配置

最終配置処理は冪等にする。

各メイン画像とサムネイルについて、次の順序で処理する。

1. 最終ファイルが存在し、SHA-256が期待値と一致する場合は、配置済みとして扱う。
2. 最終ファイルが存在し、SHA-256が一致しない場合は上書きせず、**storage_key_conflict** とする。
3. 最終ファイルが存在せず、一時ファイルが存在する場合は、同一Volume内でrenameする。
4. rename後にSHA-256、容量、形式および寸法を再検証する。
5. 一時ファイルと最終ファイルが両方存在しない場合は、**upload_required** とする。
6. 一時ファイルと最終ファイルが両方存在する場合は、最終ファイルを正として検証し、一時ファイルをGC対象にする。

**photo_operation_files.upload_status** だけを信用せず、ファイルの存在とSHA-256を確認する。

ファイルrename後・状態更新前にプロセスが停止した場合でも、再試行時に最終ファイルを検出して継続できる。

## 19. 保存確定

追加・削除・許可されたステータス変更を、1つのDBトランザクションで確定する。

1. すべての追加画像がアップロード済みか確認する。
2. 権限、現在ステータスおよび **lock_version** を事前確認する。
3. 一時ファイルを再検証する。
4. 操作状態を **committing** にする。
5. DBトランザクション外かつ開始前に、一時ファイルを最終位置へ配置する。
6. 最終位置のファイルを再検証する。
7. DBトランザクションを開始する。
8. タスク行をロックする。
9. **lock_version** を再比較する。
10. 権限と現在ステータスを再検証する。
11. 削除対象写真を論理削除する。
12. 削除後の有効写真数を取得する。
13. 「有効写真数 + 追加写真数」が8以下であることを確認する。
14. 論理削除済みを含む最大 **sort_order** から追加分を採番する。
15. 追加写真レコードを登録する。
16. 権限のあるステータス変更を適用する。
17. タスクの **lock_version** を増加させる。
18. 操作結果を **committed** として記録する。
19. DBトランザクションをコミットする。

追加・削除・ステータス変更を別トランザクションに分割しない。

一部の最終配置に失敗した場合はDBトランザクションを開始しない。

トランザクションがロールバックされた場合は、別トランザクションで操作状態を更新する。

**conflicted** または **failed_retryable** の場合は、再試行のため最終ファイルを期限まで保持する。

**failed_terminal** の場合は最終ファイルの削除を試み、失敗時はGC対象とする。

## 20. ステータス変更との組み合わせ

写真操作の可否は、タスク行をロックした時点の現在ステータスで判定する。

### 現在ステータスが未完了

- 権限があれば写真を追加・削除できる。
- 権限範囲内のステータス変更と写真変更を同じ変更セットに含められる。
- 写真変更を先に、ステータス変更を後に適用する。
- Adminは写真変更と完了への変更を同時保存できる。
- Leaderは写真変更と未着手・進行中・確認中への変更を同時保存できる。

### 現在ステータスが完了

- Adminを含め、写真を追加・削除できない。
- Adminは差し戻しだけを保存できる。
- 差し戻しと写真変更を同じ変更セットに含められない。
- 差し戻し保存後、新しい **lock_version** と **operation_id** で写真を変更する。

## 21. サーバー側画像検証

サーバーはクライアントの申告値を信用せず、受信した実ファイルから値を取得する。

### メイン画像

- MIMEタイプ: image/webp
- ファイルサイズ: 3MB以下
- 幅・高さ: 各1920px以下
- 総画素数: 3,686,400px以下
- 静止画としてデコード可能

### サムネイル

- MIMEタイプ: image/webp
- ファイルサイズ: 300KB以下
- 幅・高さ: 各480px以下
- 静止画としてデコード可能

画像処理ライブラリにはデコード時の画素数制限を設定し、制限を超えた画像を全展開しない。

DBへ保存するMIMEタイプ、容量、幅、高さおよびSHA-256は、サーバーが実ファイルから取得する。

MVPではクライアントが生成したWebPを検証して保存し、サーバー側では再エンコードしない。

## 23. 起動時リカバリー

アプリケーション起動時に、異常終了した写真操作を回収する。

MVPの本番構成は単一アプリケーションインスタンスを前提とする。

1. リカバリー処理用の排他ロックを取得する。
2. **committing** のまま残っている操作を検索する。
3. **processing_instance_id** とリース状態を確認する。
4. 前回プロセスが所有していた操作、またはリース切れの操作を回収対象にする。
5. **photo_operation_files** の一時キーと最終キーを確認する。
6. 最終位置に期待するSHA-256のファイルがあれば再利用可能として記録する。
7. DBへ写真変更がコミットされていないことを確認する。
8. 操作を **failed_retryable** へ変更する。
9. リカバリー結果を運用ログへ記録する。

成功時の写真レコード登録と **committed** への変更は同じDBトランザクションで行うため、通常は写真だけコミットされて操作状態だけ **committing** になることはない。

写真レコードが存在するにもかかわらず操作が **committing** の場合は、自動更新せず整合性エラーとして通知する。

将来アプリケーションを複数インスタンス化する場合は、インスタンスIDと分散リースによって、稼働中インスタンスの処理を回収しないようにする。

起動時処理に加えて、通常の30分無活動判定も残す。

## 24. 操作レコードの保持

- 操作の無活動期限: 30分
- 終了済み操作の最小保持期間: 72時間
- 各アップロード、再試行、競合解消で **last_activity_at** を更新する。
- **conflicted** と **failed_retryable** は30分間無活動で **aborted** にする。
- **committing** の異常終了は起動時リカバリーまたは期限切れ処理で **failed_retryable** にする。

操作レコードとファイル明細は、次の両方を満たすまで削除しない。

- 終了から72時間以上経過している。
- 全ファイルが **registered** または **cleanup_completed** である。

GCに失敗している明細がある場合は、72時間を超えても保持する。

## 25. GC

GCは1日1回実行する。

### 削除対象

- mtimeから24時間以上経過した一時ファイル
- mtimeから24時間以上経過した未参照の最終ファイル
- **deleted_at** から72時間以上経過した論理削除写真
- **failed_terminal** に紐づく未参照ファイル
- 30分以上無活動で期限切れになった **failed_retryable**
- 30分以上無活動の **aborted**
- **storage_gc_jobs.delete_after** を過ぎたファイル

**aborted**、**failed_terminal** および期限切れ操作については、**photo_operation_files** の一時キーと最終キーの両方をGC対象とする。

### 保護対象

- **reserved**
- **uploading**
- **ready**
- **committing**
- **conflicted**
- 期限内の **failed_retryable**
- **delete_after** 前のGCジョブ
- 実行中バックアップが必要とするファイル

一般的な未参照ファイル判定より、操作状態と **delete_after** を優先する。

GC成功後はファイル明細を **cleanup_completed** にする。

DB上で有効だがファイルが存在しない場合は自動削除せず、運用エラーとして記録する。

## 26. タスク削除

タスクは現行実装どおり、**tasks.deleted** に削除日時を設定して論理削除する。写真機能の追加を理由に、タスクを物理削除へ変更しない。

同じDBトランザクション内で次を行う。

1. 未削除のタスク行をロックする。
2. 削除権限を検証する。
3. 有効な写真の写真IDと保存キーを取得する。
4. 監査ログを保存する。
5. **storage_gc_jobs** を作成する。
6. **storage_gc_items** を、保存キー重複時は **ON CONFLICT DO NOTHING** で登録する。
7. 有効な写真へ、同一の削除日時と実行ユーザーを **deleted_at**、**deleted_by** として設定する。
8. タスクへ同じ削除日時を **deleted** として設定し、**lock_version** を増加させる。
9. コミットする。

写真レコードとタスク行は物理削除せず、監査・GC・復旧判断に必要な情報を保持する。

GCジョブの **delete_after** はタスクの論理削除から72時間後とする。

GCジョブと監査ログは、削除対象の写真やタスクへの外部キーを持たない。

タスク削除対象のファイルは、mtimeが24時間を超えていても **delete_after** より前に削除しない。

72時間は、バックアップの許容上限48時間に24時間の安全余裕を加えたMVP初期値とする。Volume使用量、誤削除の発見時間および復旧実績に応じて見直す。

GCは1日1回のため、排他処理や失敗がない通常時の実際の物理削除は、論理削除からおおむね72〜96時間後となる。

## 27. 画像配信

Docker Volumeを公開ディレクトリとして直接配信せず、認証付きAPIを経由する。

画像取得時に毎回次を確認する。

- ログイン状態
- 対象タスクの閲覧権限
- 対象タスクが論理削除されていないこと
- 写真が論理削除されていないこと
- 写真とタスクの関連

### 200レスポンス

```http
Cache-Control: private, no-cache
Content-Type: image/webp
Content-Length: {actual-byte-size}
ETag: "{sha256}"
X-Content-Type-Options: nosniff
```

メイン画像は **main_sha256**、サムネイルは **thumbnail_sha256** を強いETagとして使用する。

### 304レスポンス

```http
Cache-Control: private, no-cache
ETag: "{sha256}"
```

304には **Content-Type** と **Content-Length** を付与しない。

ETagを比較する前に、必ず認証・認可と論理削除状態を検証する。

論理削除によってSHA-256は変化しないが、毎回認可と論理削除状態を確認するため、削除済み画像へ304を返さない。

現行Figmaでは一覧へ多数のサムネイルを並べないため、MVPではメイン画像とサムネイルの両方に **private, no-cache** を使用する。

将来、多数のサムネイルを一覧表示する場合は、サムネイルだけ短時間キャッシュすることを再検討する。

## 28. インフラ設定

- 1写真あたりのアプリケーション上限: 4MB
- リバースプロキシのリクエスト上限: 8MB
- アップロードタイムアウト: 180秒
- 同時アップロード数: 1

リバースプロキシでは、アップロード用ルートのリクエストバッファリングを無効化する。

32MBの一括リクエスト設定は使用しない。

## 29. バックアップ

DBバックアップとマニフェストは、同一DBスナップショットから取得する。

マニフェストには次を含める。

- 写真ID
- タスクID
- メイン画像の保存キー・容量・SHA-256
- サムネイルの保存キー・容量・SHA-256
- 論理削除状態

手順:

1. バックアップとGCの排他ロックを取得する。
2. DBスナップショットを開始する。
3. 同じスナップショットからDBバックアップを取得する。
4. 同じスナップショットからマニフェストを生成する。
5. マニフェストに含まれるメイン画像とサムネイルをVolumeから取得する。
6. 件数・容量・SHA-256を検証する。
7. DB、マニフェスト、画像を同一世代として保存する。
8. 排他ロックを解放する。

バックアップ中はGCを実行しない。GC実行中は、GC完了後にバックアップを開始する。

排他ロックには有効期限とハートビートを持たせ、異常終了による永久ロックを防ぐ。

スナップショット時点で有効だった写真は、その後論理削除されてもマニフェストに含まれる。

### 運用値

- 頻度: 1日1回
- 保持: 7世代
- 通常想定所要時間: 24時間以内
- 許容上限: 48時間
- 物理ファイル削除猶予: 72時間
- Volume使用率80%で通知
- 定期的に復元テストを行う

48時間を超えたバックアップは失敗として通知する。

物理ファイル削除猶予72時間は、バックアップ許容上限48時間に24時間の安全余裕を加えた値である。MVPの初期運用値として採用し、Volume使用量と復旧実績に応じて見直す。

## 30. 復元

1. アプリケーションとGC処理を停止する。
2. リバースプロキシでメンテナンス画面を返す。
3. DBを一時環境へ復元する。
4. 同一世代のマニフェストを読み込む。
5. メイン画像とサムネイルを一時Volumeへ復元する。
6. 件数・容量・SHA-256を検証する。
7. DBレコードと保存キーの対応を確認する。
8. DBとVolumeを切り替える。
9. 整合性確認を再実行する。
10. アプリケーションを再開する。

Docker Volume自体を削除してから復元を開始してはならない。

### 復元時の判定

- DBバックアップ破損: 中止
- マニフェスト破損: 中止
- メイン画像欠損またはSHA-256不一致: 中止して運用者判断
- サムネイルだけ欠損: 復元を続行
- 欠損サムネイル: メイン画像から再生成
- 再生成後: 容量・寸法・SHA-256をDBへ反映

### サムネイル再生成時の注意

WebPエンコーダの種類やバージョンが異なる場合、同じメイン画像と設定から再生成しても、サムネイルのバイト列とSHA-256が復元前から変わることがある。

これは直ちに破損を意味しない。

再生成後の実ファイルから容量、寸法およびSHA-256を取得してDBを更新し、運用ログに次を記録する。

- 対象写真ID
- 復元前のSHA-256
- 復元後のSHA-256
- 使用したエンコーダとバージョン
- 再生成日時

以後のETagとバックアップマニフェストには、再生成後のSHA-256を使用する。

## 32. PC画面

タスク一覧に「確認」列を追加する。

固定操作列の順序:

1. 確認
2. 編集
3. 削除

確認列には写真アイコンと登録枚数バッジを表示する。

確認中のタスクに写真が1枚以上ある場合は、Leader／Adminの確認候補として最優先に強調表示する。

- 表示例: **確認中・写真 3枚**
- 写真が0枚の場合は強調しない。
- 完了済みの場合は通常の枚数表示にする。
- 未着手・進行中で写真がある場合は、作業途中の写真と区別できるよう、通常の枚数バッジを表示するが確認候補として強調しない。
- **確認中・写真あり** で一覧を絞り込めるようにする。
- 必要に応じて、ステータスを問わない **写真あり・未完了** の絞り込みも使用できるようにする。

この表示によって、写真を登録したUserと確認・ステータス操作を行うLeader／Adminが異なる場合でも、確認中の対応候補を一覧から判別できるようにする。

MVPでは「誰が閲覧したか」を意味する未読・確認済みフラグや通知配信は設けない。

### 写真確認画面

- 16:9のメイン画像
- 前へ／次へボタン
- 現在位置と総枚数
- 登録順のサムネイル
- 物品名
- 数量
- 担当者
- 備考
- 閉じるボタン
- 権限がある場合のステータス操作

写真が0枚の場合は次を表示する。

```text
登録されている写真はありません
```

PCでは確認画面内のメイン画像を使用し、さらに別の拡大モーダルは設けない。

## 33. 主なエラー

- 非対応形式
- HEIC／HEIFのデコードまたはWebP変換に失敗した
- HEIC／HEIFデコーダーの読み込みに失敗した
- 入力ファイルが20MBを超えている
- 入力画素数または長辺が上限を超えている
- ブラウザで安全に変換できない
- WebP変換に失敗した
- メイン画像を3MB以下にできない
- サムネイルを300KB以下にできない
- 最大8枚を超えている
- アップロードに失敗した
- タスクがほかのユーザーによって更新された
- 権限またはステータスが変更された
- 保存先に期待値と異なるファイルが存在する

変換フェーズでは写真ごとに再試行できる。

保存確定フェーズでは変更セット全体を再試行する。

## 36. 受け入れ条件

- JPEG・PNG・WebP・HEIC・HEIFを選択できる。
- 拡張子やMIMEタイプが不正確でも、実データからHEIC／HEIFを判定できる。
- ブラウザ標準機能でHEIC／HEIFをデコードできない場合、WASMデコーダーを遅延読み込みできる。
- HEIC／HEIFコンテナのprimary itemを端末側で静止画WebPへ変換できる。
- HEIC／HEIF変換中に処理段階を表示できる。
- HEIC／HEIFの元画像をサーバーへ送信・保存しない。
- 端末側で静止画WebPへ変換できる。
- 長辺1920px・品質82%を基本として圧縮できる。
- EXIFの向きを反映し、位置情報を削除できる。
- 最大8枚まで登録できる。
- 写真を登録順に表示できる。
- 縦写真を切り抜かずに表示できる。
- MobileとPCの両方で写真を確認できる。
- 完了中は全ロールで写真を変更できない。
- 追加・削除・ステータス変更を1つのDBトランザクションで確定できる。
- ファイルを最終位置へ配置してからDBをコミットできる。
- 保存確定の再試行でrenameが二重実行されても失敗しない。
- 同じ操作の重複実行をUNIQUE制約で防止できる。
- 競合後にアップロード済みファイルを再利用できる。
- 変換済み画像と未完了操作をIndexedDBへ保持できる。
- 新しい下書きの作成前に期限切れ下書きを削除できる。
- 端末内の写真下書きを最大3件に制限し、容量不足が見込まれる場合に古い下書きから整理できる。
- 画面ロック、別アプリへの移動、再読み込み後に写真登録を再開できる。
- **あとで** を選択した下書きを、対象タスクの詳細画面から再開できる。
- IndexedDBへ保存できない場合にデータ消失の可能性を案内できる。
- 競合時に変更内容と自分の写真が保持されていることを表示できる。
- 完了との競合時にAdminへの差し戻し依頼を案内できる。
- 保存済み写真を削除する前に削除枚数を確認できる。
- 一覧から確認中・写真ありのタスクを優先して判別できる。
- 失敗操作の一時キーと最終キーをGCが追跡できる。
- GC完了前に操作明細を削除しない。
- GC明細が重複してもタスク削除を失敗させない。
- タスク削除時にタスクと有効な写真を同じDBトランザクションで論理削除できる。
- タスク削除対象の写真ファイルを、論理削除から72時間より前に物理削除しない。
- 論理削除済みタスクの写真を画像配信APIから取得できない。
- アプリケーション再起動時に停止中の確定処理を回収できる。
- DBバックアップと画像マニフェストを同一スナップショットから生成できる。
- サムネイル再生成によるSHA-256変更を記録できる。
- 未認証ユーザーが画像へ直接アクセスできない。
